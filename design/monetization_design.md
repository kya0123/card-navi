## 1. 目的と前提

- 本アプリ（PWA）と、集客用のWeb記事を組み合わせて収益を得る方法を定める
- 現行の要件は変えない：**オフライン動作・サーバなし・利用明細を取り込まない・カード番号を保持しない**
- 推奨の中立性を最優先にする。推奨の順位が広告の報酬に左右された時点で、アプリの価値がなくなるため

---

## 2. 市場調査の要約（2026-09-24時点）

| 観点 | 内容 |
|---|---|
| クレカのアフィリエイト報酬 | SEOメディア経由で、申込み・発券1件あたり**数千円〜数万円**。ゴールドなどの上位カードや、広告主が予算を積む時期の特別単価で上がる |
| 海外の類似アプリ | CardPointers（有料プラン 年約90ドル）、MaxRewards（有料 Gold 年約108ドル）。無料版と有料版を分ける課金型 |
| 国内の類似アプリ | 「おすすめクレカ診断」型の比較アプリや管理アプリはある。**保有カードの使い分けと、年間ボーナスまで含めて最適なカードを判断する**ものは少ない |
| 規制 | ステルスマーケティング規制（景品表示法、2023年10月施行）。事業者の広告であることが一般消費者に明確に分かる表示（「広告」「PR」など）が必要 |

## 3. 収益モデルの比較と方針

| モデル | 見込み | 判定 |
|---|---|---|
| M1 クレカ発行のアフィリエイト | 1件あたりの単価が高い。本アプリは申込み意欲の高い利用者に、根拠のある提案ができる | **主軸** |
| M2 有料プラン | 日本はアプリにお金を払う人が少ない。サーバなしでは課金の仕組みも作りにくい | 将来の選択肢 |
| M3 広告表示（AdSenseなど） | 利用者が少ないうちはほぼ収益にならず、画面の見やすさを損なう | **採用しない** |
| M4 攻略記事（SEO）＋アプリ | 記事で検索から人を集め、アプリで具体的な差額を見せる | M1と組み合わせる集客手段 |

**方針**：M1を主軸、M4を集客手段とする。M3は採用しない。M2はフェーズ3で検討する（11章）。

## 5. データ設計

### 5.1 アフィリエイト情報は別ファイルにする（`master/affiliates.json`）

還元ルール（`rules.json`）には混ぜない。還元ルールの正しさと、広告の都合を分けて管理するため。

```ts
export interface AffiliateLink {
  cardId: Id;              // rules.json の cards[].id
  url: string;             // ASPが発行したリンク（公式の申込みページへ遷移）
  asp: string;             // 'a8' | 'afb' | 'accesstrade' | ... 
  label: 'PR';             // 画面に必ず表示する表記
  validFrom: YMD | null;
  validTo: YMD | null;
  checkedAt: YMD;          // リンクが有効であることを確認した日
}
export interface AffiliateMaster {
  schemaVersion: 1; version: string; links: AffiliateLink[];
}
```

- リンクがないカードは、公式サイトへの通常リンク（PR表記なし）を表示する
- 期間外（`validTo` を過ぎたもの）は通常リンクに切り替える
- ビルド時に「`cardId` がマスタにあること」「URLが https であること」を検証する
- URLの取得と更新の手順は10章

### 5.2 提案の表示状態（`meta` ストアに追加）

端末内（IndexedDB）にのみ保存し、外部へは送らない。

```ts
export interface PromoSlot {
  lastShownAt?: YMD;          // 最後に表示した日
  intervalDays: 7 | 14 | 30;  // 次に出せるまでの間隔（A：反応がなければ広げる）
  tappedSinceShown: boolean;  // 最後の表示のあとにタップされたか
  dismissedUntil?: YMD;       // ×で閉じた場合、この日まで表示しない
  lastSignature?: string;     // 最後に表示した内容の要約（B：内容が変わったかの判定）
  pendingEarly?: boolean;     // 早めに出すきっかけが発生した（③のみ）
}
export interface PromoState {
  firstLaunchAt: YMD;                   // 初回起動日
  hint: Record<Id, PromoSlot>;          // ① 店舗ごと（最近使ったお店にない店舗は削除）
  hintLastShownAt?: YMD;                // ① いずれかの店舗で最後に表示した日
  banner: PromoSlot;                    // ③
}
```

## 6. カード見直しシミュレーション（F2、`domain/simulate.ts`）

金額を入力しないため、年間の金額は出さない。**最近使ったお店**（`recentStores`、最大20件）を材料に、事実として言える指標だけを出す。

### 6.1 シグネチャ

```ts
simulateAddCard(master: MasterIndex, user: UserSettings, recent: Id[], today: YMD,
                opt = { minDelta: 0.02, topN: 3 }): SimResult[]

interface SimResult {
  cardId: Id;
  totalStores: number;        // 対象にした最近のお店の数
  improved: { storeId: Id; beforeRate: number; afterRate: number }[];  // 上がるお店（差の大きい順）
  per10kYen: number;          // 上がるお店で1万円使うごとの増加額
  breakEvenMonthlyYen: number | null;  // 年会費の回収ライン（月額）。年会費無料なら null
  annualFeeYen: number;
  bonusNote: string | null;   // 例「年100万円の利用で＋10,000ポイント」
  signature: string;          // 表示制御用（8.3）
}
```

### 6.2 計算手順

1. **現状の率**：最近のお店ごとに既存の `recommend()` を実行し、1位の `rate`（ボーナス加算なし）を `beforeRate` とする
2. **候補カード**：マスタにあり保有していないカード。全支払い方法を有効とみなす
3. **追加後の率**：保有カードに候補カードを加えた仮の設定で同じ計算をし、`afterRate` とする
4. **上がるお店**：`afterRate − beforeRate ≥ minDelta`（既定2ポイント）のお店
5. **1万円あたりの増加額** = 上がるお店の差の単純平均 × 10,000（円未満切り捨て）。金額が分からないため、お店ごとの重みは付けない
6. **年会費の回収ライン** = 年会費 ÷ 差の単純平均 ÷ 12 を100円単位で切り上げ
7. **並べ替え**：①上がるお店の数の降順 ②1万円あたりの増加額の降順 ③カードID昇順。**アフィリエイトの有無・報酬額は使わない**
8. 上がるお店が0件のカードは除外。該当なしなら「今の組み合わせで十分です」と表示する

### 6.3 表示の前提条件

- 「最近使ったお店をもとにした目安です。キャンペーン・入会特典は含みません」
- 「年会費は通常の金額で計算しています（初年度無料・条件付き無料は含みません）」
- 「最新の条件は必ず公式サイトで確認してください」

### 6.4 表現のルール

| 使う | 使わない |
|---|---|
| 「よく行くお店 8件中5件で還元アップ」「セブン-イレブン 1%→7%」「1万円ごとに＋600円」「月7,700円使えば年会費の元が取れる」「年会費無料：持つだけで損はありません」 | 「年間＋◯万円」など金額を仮定した表現、「最強」「必ず得」などの断定、根拠を示さない倍率 |

### S09 広告の方針（新規。設定画面と S07 からリンク）

- 本アプリはアフィリエイト広告で運営していること
- 推奨・見直し結果の順位は計算結果のみで決まり、広告の有無や報酬額に影響されないこと
- 利用者の情報（保有カード・最近使ったお店）は端末内にのみ保存し、外部に送らないこと

## 8. 提案の表示タイミング（F7、`domain/promo.ts`）

「急いでいない時」に「根拠がそろった時」だけ出す。頻度は **A（反応がなければ間隔を広げる）＋ B（内容が変わったら早めに出す）** で制御する。`today` は引数で受け取る（既存方針と同じ）。

### 8.1 場面ごとの条件

| 場面 | 出す条件（すべて満たす） | 頻度の単位 |
|---|---|---|
| ① 推奨直後のヒント | ・初回起動から14日以上<br>・表示中のお店で、未保有カードの最高率 − 保有カード1位の `rate` ≥ **3ポイント**<br>・その日、ほかのお店で①を出していない（1日1回まで） | お店ごと |
| ② 見直し画面 | 利用者が開いたときは常に表示（制御しない）。最近のお店が5件未満なら案内のみ | — |
| ③ ホームのバナー | ・初回起動から14日以上<br>・最近のお店が5件以上<br>・`simulateAddCard` の1位が**2件以上**のお店で上がる<br>・その日①を出していない<br>・検索欄が空 | アプリ全体で1つ |

### 8.2 A：反応がなければ間隔を広げる（①③共通）

| できごと | 状態の更新 |
|---|---|
| 表示した | 前回の表示のあとにタップがなければ `intervalDays` を 7 → 14 → 30 に1段広げる（30が上限）。`lastShownAt = today`、`tappedSinceShown = false` |
| タップした（S07へ移った） | `tappedSinceShown = true`、`intervalDays = 7` |
| ×で閉じた | `dismissedUntil = today + 60日`、`intervalDays = 30` |

初期値は `intervalDays = 7`。

### 8.3 B：内容が変わったら早めに出す（①③共通）

- 内容の要約 `signature` を比べる。① は「最高率の未保有カードID＋率」、③ は「上位3件のカードIDと上がるお店の数」
- 前回と `signature` が違えば、`intervalDays` に関係なく**前回から7日**で出せる

### 8.4 判定（`canShow`）

```ts
canShow(slot: PromoSlot, sig: string, today: YMD): boolean
```

1. `dismissedUntil` があり `today < dismissedUntil` → 出さない（×はA・Bより優先）
2. 一度も出していない → 出す
3. `days = today − lastShownAt`
4. ③で `pendingEarly = true` かつ `days ≥ 1` → 出す（出したら `pendingEarly = false`）
5. `sig ≠ lastSignature` → `days ≥ 7` なら出す（B）
6. それ以外 → `days ≥ intervalDays` なら出す（A）

### 8.5 ③を早めに出すきっかけ（`pendingEarly`）

- ボーナス期間が新しくなった（詳細設計5.4の繰り越し処理の中で立てる）
- 還元ルールの版数が変わり、③の `signature` が前回と違う

### 8.6 例（③）

| 日 | できごと | 間隔 | 次に出せる日 |
|---|---|---|---|
| 1日目 | 表示、タップなし | 7 | 8日目 |
| 8日目 | 表示、タップなし | 14 | 22日目 |
| 22日目 | 表示、タップ | 7 | 29日目 |
| 25日目 | 最近のお店が変わり上位が入れ替わる | 7 | 29日目（B） |
| 29日目 | 表示、×で閉じる | 30 | 89日目（60日後） |

## 9. 法令・規約の対応

| 項目 | 対応 |
|---|---|
| ステマ規制 | アフィリエイトリンクを置く画面・記事には「PR」を表示。記事の冒頭にも広告を含む旨を記載 |
| 有利誤認の防止 | 金額を仮定した「年+◯円」は出さない（6.4）。目安であることと前提条件を同じ画面に表示（6.3）。「必ず得」「最強」などの断定表現は使わない |
| ASPの規約 | アプリ内での掲載可否、広告主ごとの禁止表現（ポイントサイト的な誘導の禁止など）を各ASPで確認する |
| 個人情報 | 収集しない。計測（F5）を入れる場合も、個人を特定しない方法（Cookieを使わない計測ツールなど）を選び、方針ページに記載 |
| 還元情報の正確性 | マスタの確認日を表示し、古いものは警告（既存機能）。公開前に信頼度の低いルールを解消する |
| 勤務先の副業規定 | 個人で収益を得る前に、勤務先の副業規定と届出の要否を確認する |

※法令の解釈は専門家ではない立場での整理。公開前に景品表示法の運用基準と各ASPの規約を確認すること。

## 10. アフィリエイトリンクの運用手順

公開（フェーズ2）の準備として行う。自分専用のうちは不要。

### 10.1 事前準備

| No | 作業 | 内容 |
|---|---|---|
| P1 | 公開サイトの用意 | PWAを公開するドメインに、運営者情報・プライバシーポリシー・広告の方針（S09）を置く |
| P2 | 記事の用意 | 攻略記事を数本公開しておく。クレカは金融系で提携審査が厳しめのため、ツールだけのサイトより通りやすい |
| P3 | 勤務先の規定確認 | 副業規定と届出の要否を確認する（9章） |

### 10.2 リンクの取得

| No | 作業 | 内容 |
|---|---|---|
| G1 | ASPにメディア登録 | A8.net（登録審査なし）、もしもアフィリエイト、afb、アクセストレード、バリューコマース、JANet など。PWAは「Webサイト」として登録する |
| G2 | 案件の検索 | マスタのカードごとに各ASPで検索し、報酬・成果条件・掲載条件を比べる。扱う案件と単価はASP・時期で変わり、掲載のない時期もある |
| G3 | 提携申請 | 広告主の審査を受ける（数日程度）。否認された場合は、記事を増やしてから再申請するか、別のASPで申請する |
| G4 | 掲載条件の確認 | 承認後、次を確認して記録する：アプリ・PWA内での掲載可否、表示回数計測用の1×1画像タグの要否、禁止表現・指定表現、リスティング広告の可否 |
| G5 | リンク作成 | 管理画面の「広告リンク作成」でテキストリンクのURLをコピーする（A8.netの例：`https://px.a8.net/svt/ejp?a8mat=…`）。**URLは加工しない**（パラメータの追加・短縮URL化をしない） |
| G6 | 登録 | `master/affiliates.json` に `cardId`・`url`・`asp`・`checkedAt`・`validTo`（案件の終了日。未定ならnull）を記入する |
| G7 | 動作確認 | ビルド後、実機でリンクを開き、公式の申込みページに遷移すること、ASPの管理画面でクリックが計上されることを確認する |

### 10.3 使ってはいけないリンク

- **カード会社の友達紹介コード・紹介URL**：多くの場合、不特定多数への掲載や商用利用が禁止されている
- **ASPを経由しない公式ページへの独自パラメータ付きURL**

### 10.4 定期的な運用

| 頻度 | 作業 |
|---|---|
| 通知のたび | ASPから届く案件の終了・報酬変更・表現規定変更の通知を確認し、`validTo` や表示を更新する |
| ビルドのたび | リンク確認スクリプト `scripts/check_affiliates.mjs` を実行する（10.5） |
| 月1回 | ASPの管理画面でクリック数・発生・承認を確認する（13章のKPI）。同じカードを扱う別ASPの単価と比べる |
| 還元ルール更新時 | アプリが表示する率・特典が、広告主の指定表現や公式の条件とずれていないか確認する |

### 10.5 リンク確認スクリプト（`scripts/check_affiliates.mjs`）

ビルド時（ネット接続あり）に実行する。アプリ自体はオフラインのまま。

| チェック | 結果 |
|---|---|
| `cardId` がマスタにない | エラー（ビルド失敗） |
| URLが https でない | エラー |
| URLにアクセスし、リダイレクト後の応答が 4xx／5xx | 警告（案件終了の可能性） |
| `validTo` が過ぎている | 警告（アプリでは自動で通常リンクに切り替わる） |
| `validTo` まで14日以内 | 警告（更新の準備） |
| `checkedAt` から90日以上経過 | 警告（管理画面で掲載状況を再確認） |

## 13. KPIと収益の試算

| 指標 | 意味 |
|---|---|
| 月間の利用者数 | 記事とアプリの訪問者 |
| 見直し実行率 | 利用者のうちS07を開いた割合 |
| 場面ごとのタップ率 | ①ヒント・③バナーの表示のうちS07へ移った割合（端末内で数え、計測を入れる場合のみ集計） |
| ×で閉じた割合 | ①③の表示のうち×で閉じた割合。高ければ条件や頻度を見直す |
| 申込みリンクのクリック率 | S07表示のうちリンクを押した割合 |
| 発券数・報酬額 | ASPの管理画面で確認 |

**試算（仮定）**：年間の利用者1,000人 × 発券率5% × 報酬1万円 ＝ **年約50万円**。
同じ1,000人で有料プラン（年3,000円）の加入率5%なら年約15万円。

## 14. テスト観点

| 対象 | 観点 |
|---|---|
| simulateAddCard | 保有カードのみで最適なら0件。上がる幅がちょうど2ポイント／2ポイント未満の境界。並び順（お店の数 → 1万円あたり → カードID）。年会費の回収ラインの100円切り上げ。年会費無料なら null |
| 中立性 | `affiliates.json` の有無・内容を変えても、S07の順位と①③の出る・出ないが変わらないこと（ゴールデンテストで固定） |
| canShow（A） | 7 → 14 → 30 と広がり30で止まる。タップで7に戻る |
| canShow（B） | 内容が変わると、間隔が14・30でも7日で出る |
| canShow（×） | 60日間はBや早めのきっかけがあっても出ない。61日目以降は間隔30で判定 |
| ①の条件 | 3ポイントの境界。同じ日に別のお店では出ない。③と同じ日に重ならない |
| ③の条件 | 初回起動から13日目は出ない・14日目は出る。最近のお店4件では出ない。検索欄に入力中は出ない |
| 早めのきっかけ | ボーナス期間の繰り越し・ルール版数の変更で `pendingEarly` が立ち、翌日以降に1回だけ出る |
| 表記 | アフィリエイトリンクの近くに必ず「PR」が表示されること（E2E） |
| 期間切れリンク | `validTo` を過ぎたら通常リンクに切り替わること |
| リンク確認スクリプト | 10.5の各チェックが、該当するデータでエラー・警告を出すこと |
| オフライン | オフライン時も S07 の計算と①③の判定は動き、リンクは無効表示になること |
